Fundamentos

¿Qué es NEO Workflows?

Un servicio de decisiones tipadas estilo "System One": le das un documento y un workflow, y el sistema busca precedentes, le pregunta a un modelo y aplica una cascada de confianza para decidir si la respuesta pasa automático, se escala a un LLM, o va a revisión humana.

El sistema está dividido en cuatro piezas, cada una con una sola responsabilidad — es la regla más importante del proyecto: la lógica de negocio vive solo en Go, Python solo sirve y entrena el modelo, y Rust solo hace vectores.

web TypeScript · React

Las 5 pantallas que usas todos los días: Centro de control, Playground, Historial, Workflows y Fine-tuning. Habla con neo-api por HTTP y SSE — nunca directo con Rust o Python.

neo-api Go

El único lugar con lógica de negocio. Orquesta cada run (buscar → decidir → cascada), guarda la bitácora en PostgreSQL y expone todo por HTTP + eventos en vivo (SSE).

neo-vector Rust

Convierte texto en vectores y busca los documentos más parecidos (embeddings + índice usearch). No decide nada, solo encuentra precedentes.

neo-model Python

Sirve el modelo OmniJev/OneJev-0.8B para responder las preguntas del workflow, y entrena los ajustes finos (fine-tuning) cuando se lo pides.

Nota: neo-api, neo-vector y neo-model se hablan entre sí por gRPC interno (no lo ves nunca). Lo único con lo que tú interactúas es con web, en tu navegador.

Cómo se conectan entre sí, de afuera hacia adentro:

DeAProtocolo
Tu navegadorneo-apiHTTP (comandos: correr un run, lanzar un fine-tuning) + SSE (eventos en vivo: etapas, progreso)
neo-apineo-vector / neo-modelgRPC puro — nunca lo ves, pero es el mismo canal por el que viajan las trazas (ver página "Ver las trazas")
neo-apiPostgreSQLSQL — guarda cada decisión en una tabla que no se puede editar ni borrar después (append-only, a propósito)

Esta separación es la que te deja cambiar de proveedor de modelo (local o Jev, un servicio externo de decisiones) sin tocar nada del resto: neo-api habla con cualquiera de los dos exactamente igual.

Preparación

Levantar el stack

Todo corre en Docker Compose. Con GPU (RTX 4060 u otra) el modelo decide en cientos de milisegundos; sin GPU funciona igual, pero más lento.

1

Confirma que Docker Desktop está corriendo

Si no abre, o docker info falla, ábrelo manualmente y espera 20-30s a que el ícono de la bandeja deje de animarse antes de seguir.

2

Levanta el stack completo con GPU (recomendado)

Desde la raíz del repo (D:\Apps\NEO):

terminal
docker compose -f compose.yaml -f compose.gpu.yaml up -d
¿Sin GPU a la mano? Usa solo docker compose up -d — el modelo corre en CPU. Funciona para probar, pero el fine-tuning (Fase 3) sí necesita GPU.
3

Espera a que los 5 servicios queden "healthy"

La primera vez tarda — el modelo (~2.2GB) y los embeddings (~470MB) se bajan de Hugging Face y se cachean en volúmenes de Docker; las siguientes veces es mucho más rápido.

$ docker compose -f compose.yaml -f compose.gpu.yaml ps
✓ neo-api, neo-vector, neo-model, postgres, web — Up (healthy)
4

Abre la aplicación

En tu navegador: http://localhost:5173. Si ese puerto está ocupado, cámbialo con la variable NEO_WEB_PORT.

ServicioPuertoPara qué
web5173La aplicación — esto es lo que abres en el navegador.
neo-api8080API HTTP/SSE (el front le habla a esto; rara vez lo necesitas directo).
postgres5432Bitácora de decisiones (append-only).
neo-vector / neo-model50051 / 50052gRPC interno — no se abren en el navegador.
jaeger16686UI de trazas (ver página "Ver las trazas").
Importante: si editas código y quieres ver el cambio, primero reconstruye la imagen (docker compose build <servicio>) y luego recréala (up -d --no-deps <servicio>). Solo recrear sin reconstruir deja la imagen vieja corriendo.

Recorrido

Las 5 pantallas

Todo lo que haces vive en una de estas cinco pantallas, siempre en el menú de la izquierda.

Centro de control

La pantalla de inicio: salud de los 4 servicios en vivo (según /healthz), métricas (runs totales, % automático, confianza media, latencia p50) y las rutas de la cascada repartidas en porcentaje.

Playground

Donde ejecutas un run: eliges workflow, pegas o escribes un documento (o usas un ejemplo sintético) y ves cada etapa avanzar en vivo por SSE. El detalle completo está en la página siguiente.

Historial

Todos los runs anteriores — combina lo que quedó guardado en tu navegador con la bitácora real de PostgreSQL (GET /api/runs), así que sobrevive a que cierres la pestaña.

Workflows

La lista de workflows disponibles (vienen de workflows/*.yaml) y su configuración: modelo fijado por versión, cuántos precedentes busca, y qué preguntas le hace al modelo.

Fine-tuning

Entrena un ajuste LoRA sobre el modelo base con tus propios datos y mira el progreso (paso, pérdida, tiempo estimado) en vivo. Detalle completo más adelante en este manual.

Tip: la pestaña inferior izquierda ("Fuente de datos") te deja alternar entre Auto (detecta si neo-api está vivo), En vivo (fuerza el backend real) y Demo (simula todo en el navegador, útil si el stack está apagado — por ejemplo para enseñarle la interfaz a alguien sin tener Docker corriendo).

De dónde saca cada pantalla lo que muestra:

PantallaDe dónde viene
Centro de controlGET /healthz (salud) + agregados de la bitácora
PlaygroundPOST /api/runs + eventos por SSE (GET /api/runs/{id}/events)
HistoriallocalStorage del navegador (runs de esta sesión) combinado con GET /api/runs (todo lo que ya quedó en la bitácora)
WorkflowsGET /api/workflows — lo que haya en workflows/*.yaml dentro del repo
Fine-tuningPOST /api/jobs/finetune + eventos por SSE (GET /api/jobs/{id}/events)
Manual NEO Workflows3 · Recorrido
Playground

Ejecutar un run

Un "run" es una decisión completa: de un texto a una ruta de cascada, pasando por buscar precedentes y preguntarle al modelo.

1

Ve a Playground y elige el workflow

Por ejemplo clasificar-documento · v1. Cada workflow trae su propio modelo fijado por versión y sus propias preguntas — nunca latest.

2

Pega tu documento o usa un ejemplo sintético

Los botones "Contrato", "Factura vencida", "Reporte trimestral" y "Ambiguo" cargan texto de prueba al instante — útil para probar sin tener un documento real a la mano.

3

Ejecuta el run

Botón "Ejecutar run", o el atajo Ctrl + Enter. Verás tres etapas avanzar en vivo:

Buscar precedentes (neo-vector, Rust) → Decidir (neo-model/Jev, Python) → Cascada (neo-api, Go). Cada una muestra su tiempo real en milisegundos.
4

Lee el resultado

Arriba, la ruta de la cascada (Automático / Escalar a LLM / Revisión humana) con su confianza. Abajo, la respuesta a cada pregunta del workflow — ver la página siguiente para interpretarlas.

+96ms run.stage {"name":"buscar-precedentes","status":"started"}
+150ms run.stage {"name":"buscar-precedentes","status":"done","ms":54}
+150ms run.stage {"name":"decidir","status":"started"}
+605ms run.stage {"name":"decidir","status":"done","ms":455}
+606ms run.done {"run_id":"…"}

Así se ve el "Stream SSE" del Playground — no es un ejemplo inventado, son los eventos reales que manda neo-api mientras el run avanza.

Si algo falla a medio run (por ejemplo, neo-model no responde), verás un evento run.error en vez de run.done, con el mensaje de error tal cual. Ese run no queda en la bitácora — decisions solo guarda decisiones completas, nunca intentos fallidos a medias.

Los cuatro ejemplos sintéticos del Playground, por si no sabes cuál probar primero:

Contrato

Arrendamiento, plazo forzoso — para probar la categoría "contrato".

Factura vencida

Monto y fecha de pago — para probar "factura" y la pregunta de urgencia.

Reporte trimestral

Cifras de ventas — para probar la categoría "reporte".

Ambiguo

A propósito evita las palabras que delatan la categoría — bueno para ver una confianza baja de verdad.

Manual NEO Workflows4 · Playground
Cómo leer el resultado

La cascada y la confianza

Cada respuesta trae una confianza de 0 a 1; esa confianza (la más baja de todas las preguntas del run) decide la ruta.

RutaCuándoQué significa
AutomáticoConfianza ≥ 0.90 (umbral por workflow)El sistema sigue solo, sin intervención.
Escalar a LLMConfianza media (entre los dos umbrales)Se consulta a un LLM más grande antes de decidir — por ahora, el proveedor Jev está implementado pero inactivo (sin acceso todavía).
Revisión humanaConfianza < 0.60 (umbral por workflow)Un humano tiene que mirarlo antes de actuar.

Las preguntas de un workflow vienen en tres formas — vale la pena saber distinguirlas al leer un resultado:

choice

Elige una opción de una lista (ej. categoría: factura/contrato/reporte). Trae la opción elegida, la probabilidad de cada una, y una confianza propia.

score

Un valor en una escala ordenada (ej. nivel de urgencia 1-5), con su propia leyenda y confianza.

noul

Sí/No puro, un solo número entre 0 y 1. Su confianza se calcula, no viene dada: |2×noul − 1| — mientras más cerca de 0 o de 1, más seguro está.

Ejemplo real: una pregunta noul con noul: 0.216 da confianza |2×0.216−1| = 0.568 — por debajo del umbral de 0.60, así que ese run entero se va a revisión humana aunque las demás preguntas estén muy seguras.

Dos detalles que vale la pena conocer al leer un resultado:

El modelo también reporta uso

Cada respuesta trae input_tokens / output_tokens — cuánto texto procesó el modelo. No trae latencia: eso lo mide neo-api por su cuenta, en Go, y es lo que ves en cada etapa del Playground.

El modelo es intercambiable

La forma de la respuesta (choice/score/noul) imita el API público de System One a propósito — así que, si algún día hay acceso a Jev (un proveedor externo), se puede usar sin cambiar nada de esta pantalla ni de la lógica de cascada.

Entrenamiento

Entrenar un fine-tuning

Cuando el modelo base no acierta lo suficiente en tus documentos, puedes entrenarle un ajuste LoRA con ejemplos propios.

1

Ve a Fine-tuning y elige tu dataset

Un archivo con ejemplos ya etiquetados. Entre más parecidos sean a los documentos reales que vas a clasificar después, mejor generaliza el ajuste.

2

Ajusta los hiperparámetros si quieres

Épocas, tamaño de lote y tasa de aprendizaje tienen valores por defecto razonables (3 épocas, lote 4, lr=1e-4) — no hace falta tocarlos para un primer intento.

3

Lanza el job y mira el progreso en vivo

Verás el paso actual, la pérdida (loss) y el tiempo estimado restante, actualizándose en tiempo real hasta que termine.

+2.1s job.progress {"step":12,"max_steps":750,"loss":0.0003,"eta":"4m50s"}
+291s job.progress {"step":750,"max_steps":750,"loss":0.0001,"eta":"0s"}
+291s job.done {"adapter_uri":"/data/adapters/<job_id>"}
4

El adaptador queda guardado

Al terminar, se guarda versionado — pero no se usa automáticamente en los runs normales todavía. Hoy, usar un adaptador entrenado para decidir requiere un paso manual aparte; es un pendiente conocido del proyecto.

Importante: mientras un fine-tuning está corriendo, neo-model pausa la inferencia — ningún run nuevo podrá "Decidir" hasta que el entrenamiento termine. Evita lanzar un fine-tuning si hay runs urgentes pendientes.
Manual NEO Workflows6 · Fine-tuning
Observabilidad

Ver las trazas en Jaeger

Cada run deja un rastro que cruza las 4 capas — útil para ver exactamente dónde se fue el tiempo, o dónde falló algo.

1

Abre la UI de Jaeger y elige un servicio

http://localhost:16686 (corre junto con el resto del stack). En el selector "Service" elige web para ver trazas que empiezan en el navegador, o neo-api/neo-vector/neo-model para ver desde ahí.

2

Abre una traza y lee el árbol

Una traza sana de un run se ve así — cada fila es un servicio, anidado dentro del que lo llamó:

web POST
  └─ neo-api POST /api/runs
    ├─ neo-api VectorService/Search → neo-vector search
    └─ neo-api ModelService/Decide → neo-model Decide
Tip: si una traza de POST /api/runs aparece con un solo span (sin hijos), es normal: ese span es solo "se encoló el run". El run en sí corre después, en otra traza propia — búscala por tiempo o por el run_id.
Soporte

Problemas comunes

Lo que más probablemente te vas a encontrar, y qué hacer en cada caso.

"Arquitectura en vivo" muestra neo-vector o neo-model en rojo

Qué pasa: /healthz solo marca a PostgreSQL como crítico — si neo-vector o neo-model no responden, neo-api sigue funcionando pero no puede completar runs nuevos.

Qué hacer: revisa los logs de ese servicio (docker compose logs neo-model); lo más común es que siga cargando el modelo (hasta 2 minutos en frío) o que Docker Desktop se haya caído.

context deadline exceeded
Un run se queda "pensando" mucho tiempo y al final sale con error

Qué pasa: cada run tiene 30 segundos para terminar. neo-model sirve el modelo en una sola instancia de GPU, así que si varias personas corren runs al mismo tiempo, se forma una fila — medido: con 10 usuarios simultáneos, el 81% de los runs expira.

Qué hacer: por ahora, evita correr muchos runs a la vez desde el Playground. Escalar esto a más usuarios es una decisión pendiente (ver el reporte de capacidad aparte).

Docker Desktop no arranca, o un rebuild no se refleja

Qué hacer: si docker info falla, cierra Docker Desktop por completo y vuelve a abrirlo (espera 20-30s). Si reconstruiste código pero el contenedor sigue con el comportamiento viejo, es porque up -d --no-deps solo recrea con la imagen que ya existe — necesitas docker compose build <servicio> primero.
